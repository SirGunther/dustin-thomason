## Review Summary

This version adds one capability: a note's content can come from a Markdown file in one declared folder instead of only from the note's own database record. The document is read through on every open, edited in place through the existing note surface, and written back to the file. Removing it from a card removes only the reference.

Documents are chosen from a folder tree ported from Cairn, so the two applications navigate a repository the same way. One document, several, or the documents sitting directly in a folder can be selected together; the count is shown and the selection can be trimmed before anything is added. The whole selection is attached in one request and one write, because the notes store is a single large file in a synced tree.

Two changes ship alongside the feature because it could not safely ship without them. The server now binds loopback only, since it previously bound every network interface with no authentication and the new routes widen what that exposes from board data to any file under the chosen folder. `dal.js` now derives its temporary-file pattern from the section list rather than duplicating it, because this version adds the first new data section since that duplication was introduced.

### D1: Bound File Access To One Folder

Files: [Repository boundary](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/fileRepository.js), [File routes](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/server.js), [Settings tab](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/public/todolist2.js), [Boundary regression](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/tests/file-repository.test.js), [Settings regression](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/tests/settings-file-repository.test.js)

#### Problem

- **Current Behavior(s):** WorkLists knew exactly one filesystem location, its own `data` directory. Nothing else on disk could be read or written, and no setting existed to point it anywhere.
- **Expected Behavior(s):** A person names one folder once. Every Markdown document inside it, at any depth, becomes reachable. Nothing outside it is reachable by any path, and a folder that cannot be used says so instead of failing silently.

#### Requirement(s)

- The chosen folder persists across page reloads and server restarts without re-confirmation.
- Every read and write resolves through a single check that refuses anything outside the folder, including a symbolic link inside it that points elsewhere.
- A folder that does not exist, is a file, cannot be read, or overlaps the application's own `data` directory is refused with a stated reason, and the previously working value is kept.
- Before a folder is chosen, no document can be attached and the person is told that choosing one is what enables it.

#### Solution(s)

- Added `fileRepository.js` with `resolveInRoot` as the only place a repository path becomes an absolute path. No exported function accepts an already-resolved path, so the check cannot be bypassed.
- Ported Cairn's path rules (no parent segments, no backslashes, no empty segments, bounded lengths) and added `fs.realpath` containment, which Cairn does not need because a browser directory handle cannot be traversed upward while a Node path can.
- Stored the folder as a server-side setting in a new `appSettings` data section, matching how the application already stores models, pinned boards, and card templates.

#### Validation Details

**Validation Objective:** Chosen folder persists and bounds reach

These checks establish that the folder survives a reload, that documents inside it are reachable at depth, and that a folder the application must refuse is refused with an explanation rather than accepted or silently ignored.

Validation setup: Start the server with `npm run start-server` and open `http://localhost:3010`. Have `C:\dustin-thomason` available on disk.

- [ ] **Prove:** The application reports a chosen folder as readable and remembers it across a reload.
  - **Action:** Open the left side panel, select `Settings`, select the `Files` tab, enter `C:\dustin-thomason` in `File repository folder`, select `Save folder`, then reload the browser and reopen the same tab.
  - **Expected:** The status line reads `Folder is readable. Documents inside it can be attached.` before the reload, and after the reload the field still contains `C:\dustin-thomason` with the same status line. No prompt or re-confirmation appears.
- [ ] **Prove:** Documents nested several levels inside the folder are offered, and generated copies are not.
  - **Action:** Open any card's notes pane, select the ellipsis in the notes-pane header, select `Attach document`, and type `git-commit-workflow` into the filter.
  - **Expected:** `agents/rules/git-commit-workflow.md` appears in the list. Clearing the filter and typing `.claude` returns no results, because dot-prefixed folders hold generated copies and are excluded.
- [ ] **Prove:** A folder the application cannot use is refused and the working value is kept.
  - **Action:** In the `Files` tab, replace the folder with `C:\dustin-thomason\README.md` and select `Save folder`.
  - **Expected:** The status line turns red and reads `That path is a file, not a folder.` Closing and reopening Settings shows `C:\dustin-thomason` still saved.

### D2: Attach An Existing Document To Cards

Files: [Tree, picker and batch client](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/public/fileAttachments.js), [Notes wiring](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/public/todolist2.js), [Batch route](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/server.js), [Menu extension point](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/public/cardActions.js), [Tree styling](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/public/todoliststyles2.css), [Tree regression](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/tests/file-picker-tree.test.js), [Attach regression](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/tests/file-attachments.test.js)

#### Problem

- **Current Behavior(s):** The only way to put content beside a card was to type or paste it into a new note. A document that already existed had to be duplicated, and the duplicate began diverging from the original immediately. The first cut of this feature let one document be picked at a time from a flat list, which does not serve a folder of related documents.
- **Expected Behavior(s):** One document, several, or a whole folder's worth can be pulled onto a card in a single action. Each becomes its own note, looking and behaving like every other note and showing the content currently in the file. The person sees what they are about to add, and can change their mind, before anything is added.

#### Requirement(s)

- The attach action is reached from the card ellipsis, alongside the existing items, and appears on no other card surface.
- The repository is navigated as a folder tree, matching Cairn, with a filter for search.
- Several documents can be selected at once. Selecting a folder selects the documents directly inside it; it never reaches into subfolders and never attaches the folder itself.
- The count is visible before committing, and any file in the selection can be unticked.
- An attached document uses the same editing surface and the same controls, in the same places, as an ordinary note.
- The content shown is read from the file when the card opens, not copied when the document was attached.
- Attaching the same document to the same card twice is refused rather than producing two notes.
- When part of a selection could not be attached, the person is told how many and why.
- A document that has since been moved or deleted says it cannot be found instead of rendering as blank.

#### Solution(s)

- Added the attach item through `extraActions`, the same extension point the existing `Collapse all notes` item uses, so shared board-card actions were not touched.
- Ported Cairn's explorer into the picker: nesting, folders above files in natural-name order, recursive child counts, and the same indentation and chevron behaviour. Every ported piece names its Cairn origin in the code, and a test asserts those pointers are still present. Left behind: Cairn's dirty and checked-out status, inline create and rename, drag, and workspace-root removal.
- A folder's checkbox selects its direct children only, while its row shows the recursive count. The two numbers differ deliberately, and a test asserts both together so a later change cannot make one follow the other.
- The footer states the selection size; above ten it calls the number out, above twenty-five it disables Attach. Both thresholds arrive with the listing rather than being written into the client, so one copy exists. The server enforces the ceiling independently.
- The whole selection goes to `POST /api/files/attach` as one request and one write, because the notes section is a single large JSON file in a synced tree. Each path is validated and read individually, so a bad path is reported against itself while the rest still attach.

### D3: Edit An Attached Document In Place

Files: [Save routing](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/public/todolist2.js), [Write and precondition](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/fileRepository.js), [Write route](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/server.js), [Save regression](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/tests/file-attachments.test.js), [End-to-end scenario](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/tests/browser-notes-smoke.js)

#### Problem

- **Current Behavior(s):** A note's text could only be saved back into its own database record. There was no way for an edit made in WorkLists to reach a file on disk.
- **Expected Behavior(s):** Editing an attached document changes the actual file, so opening that file in any other editor shows the change. Merely reading the document changes nothing.

#### Requirement(s)

- A saved edit is written to the file, and the note record's own text stays empty so no second copy exists.
- Opening, scrolling, or switching view modes without typing writes nothing.
- If the file changed on disk since it was opened, the save is refused and the person's typing is not lost.
- A file that cannot be written names the specific reason.

#### Solution(s)

- `saveNoteInlineEditor` now branches on the note's `source`: with one, it calls the file write route instead of the note update route.
- The write carries the modification time read when the document loaded. A mismatch returns HTTP 409 with the current time and writes nothing, mirroring the precondition the note checklist endpoint already used.
- The conflict branch deliberately does not re-render, because re-rendering would rebuild the editor from stored text and discard what the person typed.

#### Validation Details

**Validation Objective:** Edits reach disk, reads do not

These checks establish the central behaviour of the version, that a save lands in the real file, and its two safety properties: reading is not a write, and a conflicting save neither overwrites nor discards.

Validation setup: Complete D1 and D2. Open a terminal at `C:\dustin-thomason` and run `git status` first so you have a clean baseline to compare against. Editing writes to a real file in that repository.

- [ ] **Prove:** An edit made in a card changes the file on disk.
  - **Action:** Attach `agents/rules/dnu-folders.md` to a card, click into its body, type `VALIDATION TEST` at the end of the first paragraph, then click on a different note in the same pane.
  - **Expected:** A toast reads `Saved dnu-folders.md.` and `git status` in `C:\dustin-thomason` now lists `agents/rules/dnu-folders.md` as modified. Opening that file in any editor shows `VALIDATION TEST`.
- [ ] **Prove:** Reading an attached document does not write to it.
  - **Action:** Run `git checkout agents/rules/dnu-folders.md` to restore it and confirm `git status` is clean. Reopen the card, scroll the attached note, switch it between `Preview`, `Split`, and `Source`, then click another note without typing.
  - **Expected:** `git status` still reports no changes to that file.
- [ ] **Prove:** A save is refused when the file changed underneath, and the typing survives.
  - **Action:** With the card open, edit `agents/rules/dnu-folders.md` in a separate editor and save it there. Then type `SECOND EDIT` into the note in WorkLists and click another note.
  - **Expected:** A toast explains that the document changed on disk since it was opened, the text `SECOND EDIT` is still visible in the note's editor, and the separate editor's version of the file is intact. Restore the file with `git checkout` afterwards.

### D6: Keep AI Writers Away From Documents

Files: [Job guards](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/server.js), [Note update guard](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/server.js), [Control suppression](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/public/todolist2.js), [Unreachability regression](../../../../Users/dktho/OneDrive/SCRIPTS%20ALL%20SYSTEMS/To%20Do%20List/WorkLists/tests/file-attachments.test.js)

#### Problem

- **Current Behavior(s):** Every note could be rewritten by the AI refine and Prompt Injection actions, which replace the note's text with model output.
- **Expected Behavior(s):** Those actions cannot operate on a note whose content is a repository file. The chosen folder contains the fifteen authored rule files that govern how every agent in this workspace behaves, so a model rewriting one would land as a real commit.

#### Requirement(s)

- The AI actions are not offered on an attached document.
- The underlying routes and background jobs refuse an attached document even if reached directly.
- The same actions continue to work normally on ordinary notes.
