# PRDV-16402 — Transcode additional video uploads to submitted AJSFs

**ClickUp:** [PRDV-16402](https://app.clickup.com/t/43227262/PRDV-16402)

**Companion:** [[nebula/video-transcode/PRDV-16398-nova-applies-selected-transcode-preset]] — Nova applies the selected preset from the outbox event

---

## Summary

When an LTR uploads files to an **already submitted** Atlas Job Submission Form (AJSF) via the submitted-jobs tab, Callisto today finalizes the multipart upload, persists the file, audits, and publishes the legacy SQS proceeding-file-upload event — but it does **not** write `callisto.proceeding.file.video-transcode-requested.v1` to the outbox.

Video transcode outbox emission exists only on **form submit** (`SubmitJobSubmissionFormTS`), which covers files uploaded while the form was still pending. Files uploaded after submit never enter Nova’s transcode pipeline.

This story extends `POST /proceeding-job-submission/upload-complete-completed` so eligible video uploads on a submitted form emit the same command-driven outbox events as submit, using the form’s stored conversion selection (Standard / Video Mix).

---

## User story

As an LTR videographer, I want files uploaded to the submitted jobs tab of the AJSF to also be transcoded matching the conversion specs from the initial submission, so that all files I upload for a job are transcoded for the video team.

---

## Acceptance Criteria

- [ ] All eligible video files uploaded to a submitted AJSF (completed-jobs / `upload-complete-completed` path) are requested for transcode with the **same** `videoTranscode` selection stored on that job submission form
- [ ] Eligibility matches submit: form selection is Standard or Video Mix; file is on the Video track; MIME is `video/%`; feature flag `IS_VIDEO_TRANSCODE_ENABLED` is on
- [ ] Outbox event type/payload matches the existing submit path (`callisto.proceeding.file.video-transcode-requested.v1` via `JobSubmissionVideoTranscodeRequestedOutboxWriter`)
- [ ] Non-video uploads, ineligible presets (e.g. None, Site Survey), and feature-flag-off cases create the file as today but write **no** video-transcode outbox row
- [ ] Pending upload path (`POST .../upload-complete`) remains unchanged (no outbox on pending complete — submit still owns batch emission)
- [ ] Legacy SQS `ProceedingFileUploadDispatcher` behavior on the completed path is unchanged

---

## Current behavior (gap)

| Path | Endpoint / entry | File persist | Video-transcode outbox |
| --- | --- | --- | --- |
| Pending upload complete | `POST /proceeding-job-submission/upload-complete` | Yes | No |
| Form submit | `JobSubmissionService.submitJob` → `SubmitJobSubmissionFormTS` | N/A (status flip) | Yes — all eligible videos on the form |
| Completed upload complete | `POST /proceeding-job-submission/upload-complete-completed` | Yes + legacy SQS file-upload | **No** ← gap |

Completed path today (`MultiPartUploadProceedingJobSubmissionFileCompleteUploadService.uploadCompleteForCompletedJobSubmission`):

1. `createProceedingFile` (S3 complete + proceeding file + JSF file-attachment link)
2. Audit created event
3. `proceedingAggregator.dispatchProceedingFileUpload` → SQS producer (not outbox)

---

## Design decisions

1. **Emit only for the newly uploaded file** — do not re-query/re-emit all videos on the form. Submit already requested those; re-emitting would risk duplicate Nova work (deterministic event IDs may dedupe some cases, but single-file emit is the correct command-driven semantics for “this upload”).
2. **Reuse submit’s outbox stack** — `IsVideoTranscodeSelectionEligibleForOutbox`, `JOB_SUBMISSION_VIDEO_TRANSCODE_OUTBOX_WRITER_TOKEN` / `JobSubmissionVideoTranscodeRequestedOutboxWriter`, and the same feature flag. No new event type.
3. **Keep legacy SQS dispatch** — outbox is additive for Nova; SQS proceeding-file-upload stays for existing consumers.
4. **Preset source of truth** — load the job submission form’s `videoTranscode` (and `jobId` / `jobDate`) at complete time; do not trust a client-supplied preset.

## Proposed flow

```
POST /proceeding-job-submission/upload-complete-completed
    │
    ▼
UploadCompleteProceedingCompletedJobSubmissionAction
    │
    ▼
MultiPartUploadProceedingJobSubmissionFileCompleteUploadService
    .uploadCompleteForCompletedJobSubmission
    │
    ├── createProceedingFile(...)           (existing)
    ├── dispatchFileAuditCreatedEvent(...)  (existing)
    ├── dispatchProceedingFileUpload(...)   (existing SQS — keep)
    │
    └── WriteCompletedJobSubmissionVideoTranscodeOutboxTS.apply(...)
            │
            ├── skip if !isVideoTranscodeOutboxEnabled
            ├── FetchJobSubmissionFormTS / form load (videoTranscode, jobId, jobDate)
            ├── IsVideoTranscodeSelectionEligibleForOutbox.apply(videoTranscode)
            ├── skip if file not Video track or MIME not video/*
            ├── build JobSubmissionFormFileForVideoTranscodeOutboxProjection[]
            │     (single newly created file only)
            └── JobSubmissionVideoTranscodeOutboxWriterPort.writeRequestedEvents(...)
```

| Area | Path |

**Key assertions:**

- Given eligible form (Standard or Video Mix) + video MIME + Video track + flag on → `writeRequestedEvents` called once with that file and form’s preset
- Given Video Mix on the form → outbox payload `videoTranscodeValue` is Video Mix (not hardcoded Standard)
- Given Site Survey / None / null → writer not called
- Given non-`video/%` MIME or non-Video track → writer not called
- Given flag off → writer not called; file create + SQS still run
- Pending `uploadCompleteForPendingJobSubmission` still does not call the writer

## Scope boundaries

- **In:** Callisto completed AJSF upload → outbox video-transcode-requested for the new file
- **Out:** Pending upload-complete outbox (submit remains the batch emitter)
- **Out:** Changing Nova, protocol schemas, or legacy SQS proceeding-file-upload
- **Out:** Backfilling historical post-submit uploads that never got outbox rows (call out separately if product wants a one-off replay)
