### 2026-07-30 — Manual-test triage (diagnostic, docs only)

Artifact: `investigations/PRDV-16402-upload-location-failure-analysis.md`

A manual test on `atlas-dev` produced no conversion. **Root cause: wrong upload surface, not a code defect.** The URL used (`/callisto-stuff/job/5019/proceeding/897?tab=submission-files`) is the **Proceeding Detail** page → `POST /proceedings/upload-complete` (`proceedings` module); the change adds the emit to `POST /proceeding-job-submission/upload-complete-completed` (`proceeding-job-submission` module) only. **Second, independent cause:** files created on that path get no `job_submission_form_file_attachments` row — sole writer is `JobSubmissionFormFileAttachmentAssembler`, called only from the AJSF upload service — and the new by-file-id lookup is rooted at that table, so the file is unaddressable by this design even if the emit call were pasted in. Both paths share the *same* `UploadCompleteProceedingFileTransactionScript`, so the resulting file row is indistinguishable in the UI; the only difference is that invisible link row. **Deployment hypothesis refuted:** dev does not track `main` — last successful dev deploy is `d97b1c4e` (2026-07-28T19:19Z), which contains the feature; the `3ecab1b8` deploy (2026-07-29T21:14Z) failed at `RegisterTaskDefinition` on a trailing space in the image tag and did not change the service. **Two gates untested because never reached:** the Cognito feature flag and the form's preset. **Ledger correction to report §8 A14:** that assumption closed the import graph for *the submitted AJSF page* and was correct as scoped; it never enumerated every surface that can put a file in a proceeding — the analysis supplies that map (5 endpoints, 6 surfaces, 1 covered). Scope question raised with Product rather than absorbed: the ticket says "the submitted jobs tab of the AJSF" (covered), the Original Request says "all files I upload for a job" (not). No implementation-repo file touched.
