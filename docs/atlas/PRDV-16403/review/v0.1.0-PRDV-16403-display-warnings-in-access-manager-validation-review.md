### D1: Endpoint Returns Four Warning Values

Files: `callisto-back-end/src/granting-client-access/contacts/infrastructure/repositories/access-manager-warnings.repository.ts`, `.../domain/transaction-scripts/fetch-access-manager-warnings-ts/`, `.../application/controllers/actions/access-manager-warnings-action/`

#### Problem

- **Current Behavior(s):** No read path exists from `contacts.warning`, `firms.warning`, `cases.warning` or `cases.remarks_html` to any HTTP surface. Atlas cannot obtain these values at all.
- **Expected Behavior(s):** `GET /granting-client-access/contacts/contactId/:contactId/proceedingId/:proceedingId/warnings` returns `{ case: { warning }, contact: { warning }, firm: { warning }, caseRemarks: { html } }`, with empty and whitespace values normalized to null.

#### Requirement(s)

- One request returns all four values, so the panel has a single atomic success or failure.
- The contact and firm resolve from the contact id; the case resolves from the proceeding id through its job.
- Empty strings and nulls collapse to one representation, because the source columns disagree on nullability.

#### Solution(s)

- A repository holding both queries, called twice by one transaction script, since the architecture rules forbid one script calling another.
- An application-layer mapper performs the normalization, because repositories and services may not import mappers.
- Built on `FetchClientAccessListAction` as the template rather than the action named in the specification, which lacks a mapper and a guard.

#### Validation Details

- [ ] Endpoint returns 200 with all four populated for a fully seeded contact, firm, and case
- [ ] Empty strings on contacts and firms arrive as null in the response
- [ ] Whitespace-only values arrive as null
- [ ] A contact with no matching firm returns a null firm warning rather than an error

### D2: Panel Renders Four Sections Ordered

Files: `atlas-front-end/src/callisto/.../AccessManagerOverlay/components/RbWarningsPanel.vue`, `.../AccessManagerOverlay.vue`

#### Problem

- **Current Behavior(s):** The right-hand panel shows one sentence: "Warnings and notes will appear here in a future release."
- **Expected Behavior(s):** The panel shows Case warnings, Contact warnings, Firm warnings, then Case remarks, each with its value, reached from both entry points into the Access Manager.

#### Requirement(s)

- The four sections appear in a fixed order every time.
- Each value belongs to the right entity: the case behind the proceeding being viewed, the contact being granted access, and that contact's firm.
- Reopening for the same contact re-reads rather than showing cached values.

#### Solution(s)

- A new panel component replacing the placeholder paragraph, receiving values from a new Vue Query composable.
- Section headings taken from Figma, which uses plural and sentence case, rather than the specification's wording.
- Freshness comes from the overlay unmounting on close, so the query re-runs on each open; `gcTime: 0` prevents the previous contact's values painting from cache first.

#### Validation Details

- [ ] Order is Case, Contact, Firm, Case remarks
- [ ] Entry point one, the contact search panel, shows correct values
- [ ] Entry point two, the Client Access list row, shows the same values for the same contact
- [ ] Changing a warning in the database and reopening shows the new value with no page reload

### D3: Empty Sections State Absence Explicitly

Files: `atlas-front-end/src/callisto/.../components/RbWarningsPanel.vue`, `atlas-front-end/src/i18n/en-US/common.json`

#### Problem

- **Current Behavior(s):** No empty state exists, because no section exists.
- **Expected Behavior(s):** An unpopulated warning reads "None"; unpopulated case remarks read "No remarks info". Both are italic and de-emphasized, and every section stays labelled even with nothing to report.

#### Requirement(s)

- A user must never read blank space as "no warning recorded"; absence has to be stated.
- Warnings and remarks use different wording, because users refer to them differently.

#### Solution(s)

- Warnings use "None", taken from Figma. Remarks use "No remarks info", specified by Shaye Lankford in the ticket.
- Empty styling uses the overlay's existing de-emphasis token rather than the specification's "50% grey", which matches no token in the codebase.

#### Validation Details

- [ ] An empty warning shows "None", not blank space
- [ ] Empty remarks show "No remarks info", textually different from the warnings wording
- [ ] All four headings remain visible when every value is empty

### D4: Failed Fetch Never Reads Empty

Files: `atlas-front-end/src/callisto/.../components/RbWarningsPanel.vue`, `.../composables/useAccessManagerWarnings.ts`

#### Problem

- **Current Behavior(s):** No fetch exists, so no failure state exists.
- **Expected Behavior(s):** When the request fails, the panel shows "Warnings/remarks failed to load" in place of all four sections, and the user can still complete the access work.

#### Requirement(s)

- A failure must never be indistinguishable from an empty record; that confusion is the defect this objective exists to prevent.
- The failure message replaces the sections rather than sitting beside empty ones.
- A slow or failed warnings request must not block the rest of the Access Manager.

#### Solution(s)

- The panel branches on error first, before loading and before the sections, so no empty state can render during a failure.
- The warnings query is deliberately kept out of the overlay's loading state, which is fed only by the tracks query.
- Failure wording specified by Shaye Lankford in the ticket.

#### Validation Details

- [ ] A 500 response shows the failure message and no sections
- [ ] A timeout behaves the same way
- [ ] Neither empty wording appears anywhere during a failure
- [ ] The overlay still opens and the access controls still work while the warnings request is slow

### D5: Case Remarks Render Sanitized And Contained

Files: `atlas-front-end/src/callisto/.../components/RbWarningsPanel.vue`, `.../RbWarningsPanel.module.scss`

#### Problem

- **Current Behavior(s):** No remarks are rendered. Nothing in the codebase renders RB-authored HTML.
- **Expected Behavior(s):** Remarks display with their emphasis intact — colour, bolding, size — while anything that would act rather than be read is removed, and the markup cannot affect anything outside the panel.

#### Requirement(s)

- Raw RB HTML must never reach the page; it is always routed through a sanitizer.
- The emphasis an author applied survives, because that emphasis carries meaning.
- Remarks markup changes only the remarks.

#### Solution(s)

- Sanitized with DOMPurify called bare, following the specification and the repository's only other HTML-rendering site. The allowlist in the ClickUp ticket was not applied: it adds no safety, since the bare call already removes everything the criteria forbid, and it would silently drop formatting nobody agreed to drop.
- Rendered inside a contained wrapper so width and overflow cannot escape the panel.

#### Validation Details

- [ ] **This objective cannot be closed by the test suite.** DOMPurify does not sanitize correctly in the test environment: probed directly, `<p>Safe</p><script>x=1</script>` returns `Safe<script>x=1</script>`, removing the safe tag and keeping the script. The component tests therefore prove only that raw HTML is always routed through the sanitizer.
- [ ] Verify in a browser that a script tag does not execute and does not reach the page
- [ ] Verify an inline event handler is removed
- [ ] Verify an iframe is removed
- [ ] Verify colour, bolding and font size survive
- [ ] Verify a wide unbroken string does not widen the overlay

### D6: Long Content Scrolls Inside Panel

Files: `atlas-front-end/src/callisto/.../components/RbWarningsPanel.module.scss`

#### Problem

- **Current Behavior(s):** The panel's parent column is `overflow: hidden`, so content taller than the column is clipped with no scrollbar and no indication anything is missing.
- **Expected Behavior(s):** Content taller than the panel scrolls inside it, and the Save and Cancel controls stay reachable.

#### Requirement(s)

- A warning or remark longer than the available space can be read in full.
- Reading it does not displace the access work.

#### Solution(s)

- The panel owns its own scrolling element, since the parent column clips. The specification asked for internal scroll but named the parent column, which cannot provide it.

#### Validation Details

- [ ] A remarks value many times the panel height scrolls inside the panel
- [ ] Save and Cancel remain reachable while scrolled
- [ ] The page body does not scroll sideways

### D7: Repository Queries Verified Against Database

Files: `callisto-back-end/src/granting-client-access/contacts/infrastructure/repositories/__specs__/access-manager-warnings.repository.integration.spec.ts`, `.../test-utils/integration-test-helpers/seeds/`

#### Problem

- **Current Behavior(s):** The two SQL queries have never executed. Both sibling repositories in the same folder carry integration specs; this one did not, which is the mirror-coverage gap the review patterns call out.
- **Expected Behavior(s):** Both queries run against real Postgres and behave correctly for a populated case, a null case, a dangling firm reference, an inactive contact, and empty values.

#### Requirement(s)

- The join to the case must be a left join, or a proceeding whose job has no case would disappear entirely.
- An inactive contact must be unreadable.
- Empty strings must survive the query so the mapper can normalize them.

#### Solution(s)

- Integration spec written with nine cases covering both queries.
- Four seeder changes to support it: a warning value on the firm seeder, a warning value on the contact seeder inserted at the correct positional parameter, a case reference on the proceeding seeder, and a new case seeder, since none existed.

#### Validation Details

- [x] Ran `npm run test:integration -- src/granting-client-access/contacts/infrastructure/repositories/access-manager-warnings.repository.integration.spec.ts` on 2026-08-21 against local Postgres — **9 of 9 passed**
- [x] Ran the whole repository folder to confirm nothing else moved — **4 suites, 28 tests passed**
- [x] Populated case returns its warning and remarks html
- [x] Null case columns return nulls rather than dropping the row
- [x] A proceeding whose job has no case still returns a row, proving the left join
- [x] A dangling firm reference returns a null firm warning
- [x] An inactive contact is unreadable, and a missing contact returns null
- [x] Empty strings survive the query so the mapper can normalize them
- **One defect found and fixed while running it:** the spec omitted `CaseRestrictionLevel` from its entity list, and `Case` declares a relation to it, so TypeORM failed to build metadata and the suite could not start. Registering that entity fixed it. The earlier connectivity block had masked this.
