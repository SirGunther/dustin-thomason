```sql
-- 1. A firm with a warning.
INSERT INTO callisto.firms (id, name, address, city, state, zip, country, directions,
       main_phone, alt_phone, toll_free_phone, fax, firm_type_id, warning, is_active,
       created_at, updated_at)
VALUES (9001, 'Tool Time LLP', '123 Binford Ave', 'Detroit', 'MI', '48201', 'US', '',
        '', '', '', '', 1, 'Firm is on credit hold - confirm before releasing', true,
        now(), now())
ON CONFLICT (id) DO UPDATE SET warning = EXCLUDED.warning;

-- 2. Give the named contact a warning and attach it to that firm.
--    The id is explicit on purpose: an earlier version selected whichever active
--    contact sorted lowest, so the script could not tell you which row it hit.
UPDATE callisto.contacts
SET warning = 'Do not release deliverables before payment clears',
    account_id = 9001
WHERE id = 800001;

-- 3. Give the case a warning and remarks.
UPDATE callisto.cases
SET warning = 'Protective order in place - do not release to opposing counsel',
    remarks_html = '<p style="color:#b00"><strong>Rush</strong> delivery agreed with counsel.</p>'
WHERE id = 1001;

-- 4. Confirm the seed. Expect exactly one row, for contact 800001.
SELECT ct.id AS contact_id, ct.full_name, ct.warning AS contact_warning,
       f.name AS firm, f.warning AS firm_warning,
       cs.warning AS case_warning, cs.remarks_html
FROM callisto.contacts ct
LEFT JOIN callisto.firms f ON f.id = ct.account_id
CROSS JOIN callisto.cases cs
WHERE ct.id = 800001 AND cs.id = 1001;
```

### D1: Endpoint Returns Four Warning Values

Files: [Warnings repository](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/infrastructure/repositories/access-manager-warnings.repository.ts), [Transaction script](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/domain/transaction-scripts/fetch-access-manager-warnings-ts/fetch-access-manager-warnings.transaction.script.ts), [Response mapper](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/application/controllers/actions/access-manager-warnings-action/access-manager-warnings.mapper.ts), [Action](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/application/controllers/actions/access-manager-warnings-action/fetch-access-manager-warnings.action.ts)

#### Problem

- **Current Behavior(s):** No read path exists from `contacts.warning`, `firms.warning`, `cases.warning` or `cases.remarks_html` to any HTTP surface, so Atlas cannot obtain these values.
- **Expected Behavior(s):** `GET /callisto/granting-client-access/contacts/contactId/:contactId/proceedingId/:proceedingId/warnings` returns all four values in one nested response, with empty and whitespace values reported as null.

#### Requirement(s)

- One request returns all four values, so the panel has a single atomic success or failure.
- The contact and firm resolve from the contact id; the case resolves from the proceeding id through its job.
- Empty strings and nulls collapse to one representation, because the source columns disagree on nullability.

#### Solution(s)

- A repository holding both queries, called twice by one transaction script, because the architecture rules forbid one script calling another.
- An application-layer mapper performs the normalization, because repositories and services may not import mappers.
- Built on `FetchClientAccessListAction` as the template rather than the action the specification names, which has neither a mapper nor a guard.

#### Validation Details

Validation setup: Run the shared seed statement and note the contact id it returns. Open `http://localhost:9000/callisto-stuff/job/112233/proceeding/3001?tab=client-access` with devtools open on the Network tab, filtered to `warnings`. Read the response from that request rather than calling the endpoint directly — a direct `fetch` from the page is refused by CORS, and a bare `curl` returns 401 because the global guard rejects unauthenticated requests before routing.

- [ ] **Action:** Open the Access Manager for the seeded contact via contact search, then select the `warnings` request in the Network tab and read its Response. **Expected:** HTTP 200, and the body is exactly `{"case":{"warning":"Protective order in place - do not release to opposing counsel"},"contact":{"warning":"Do not release deliverables before payment clears"},"firm":{"warning":"Firm is on credit hold - confirm before releasing"},"caseRemarks":{"html":"<p style=\"color:#b00\"><strong>Rush</strong> delivery agreed with counsel.</p>"}}`. **Proves:** All four values survive the full read path - two separate SQL queries, one transaction script, and the mapper - and arrive under the nested shape the frontend binds to. A single wrong key or a flattened object fails here even when every value is correct.
- [ ] **Action:** Confirm the request URL in the Network tab. **Expected:** The path ends `/granting-client-access/contacts/contactId/<seeded-contact-id>/proceedingId/3001/warnings`. **Proves:** The action is registered on the exact path Atlas's URL builder produces, so the two repositories agree on the contract. A route that exists in code but not at this path would 404 here.
- [ ] **Action:** Run `UPDATE callisto.contacts SET warning = '' WHERE id = <seeded-contact-id>;` close and reopen the Access Manager, and read the new response. **Expected:** `contact.warning` is `null`, not `""`. **Proves:** The mapper's normalization runs on `contacts.warning`, a NOT NULL column that RB fills with `''` when unset. Without it the frontend receives an empty string, which is truthy to a presence check, and renders a blank section instead of "None".
- [ ] **Action:** Run `UPDATE callisto.contacts SET warning = '   ' WHERE id = <seeded-contact-id>;` and repeat. **Expected:** `contact.warning` is `null`. **Proves:** Normalization trims before testing for emptiness, so whitespace-only RB data is treated as absent rather than present. This is the case a plain length check would pass and get wrong.
- [ ] **Action:** Run `UPDATE callisto.contacts SET account_id = 424242 WHERE id = <seeded-contact-id>;` and repeat. **Expected:** HTTP 200 with `firm.warning` as `null`; no 500 and no error banner. **Proves:** The firm join is a LEFT join and `contacts.account_id` carries no foreign key, so an unmatched firm degrades to one null section rather than failing the whole request. Separates "this contact has no firm" from "the endpoint is broken".
- [ ] **Action:** Restore the seed with `UPDATE callisto.contacts SET warning = 'Do not release deliverables before payment clears', account_id = 9001 WHERE id = <seeded-contact-id>;` and reopen. **Expected:** The first check passes again. **Proves:** The destructive checks above are reversible and the environment is back to a known state, so a later objective's failure cannot be caused by leftover edits from this one.

### D2: Panel Renders Four Sections Ordered

Files: [Warnings panel](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/components/RbWarningsPanel.vue), [Access Manager overlay](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/AccessManagerOverlay.vue), [Warnings composable](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/composables/useAccessManagerWarnings.ts)

#### Problem

- **Current Behavior(s):** The right-hand panel shows one sentence: "Warnings and notes will appear here in a future release."
- **Expected Behavior(s):** The panel shows Case warnings, Contact warnings, Firm warnings, then Case remarks, each with its seeded value, and re-reads on every open.

#### Requirement(s)

- The four sections appear in a fixed order every time.
- Each value belongs to the right entity: the case behind the proceeding, the contact being granted access, and that contact's firm.
- Reopening for the same contact re-reads rather than showing cached values.

#### Solution(s)

- A new panel component replacing the placeholder paragraph, fed by a new Vue Query composable.
- Section headings taken from Figma, which uses plural and sentence case, rather than the specification's wording.
- Freshness comes from the overlay unmounting on close, so the query re-runs on each open; `gcTime: 0` prevents the previous contact's values painting from cache first.

#### Validation Details

Validation setup: Run the shared seed statement. Open `http://localhost:9000/callisto-stuff/job/112233/proceeding/3001?tab=client-access`.

- [ ] **Action:** Open the contact management panel, search the seeded contact by name, and select it. **Expected:** The right-hand panel shows four headings top to bottom in this order — "Case warnings", "Contact warnings", "Firm warnings", "Case remarks" — and the placeholder sentence is gone. **Proves:** The new component replaced the shipped placeholder rather than rendering alongside it, and the sections appear in the order Figma specifies. Order is a design requirement - it is the sequence the design chose for reading - not an incidental rendering detail.
- [ ] **Action:** Read each section body. **Expected:** Case warnings reads "Protective order in place - do not release to opposing counsel"; Contact warnings reads "Do not release deliverables before payment clears"; Firm warnings reads "Firm is on credit hold - confirm before releasing"; Case remarks reads "Rush delivery agreed with counsel." with "Rush" bold and the text red. **Proves:** Each value is bound to its own section rather than all four reading from one field, and the remarks path renders HTML while the three warning paths render plain text. Four correct strings in the wrong four sections would satisfy a weaker check.
- [ ] **Action:** Look at the top of the panel and its close control. **Expected:** "Warnings and notes" appears exactly once, above the four sections, and the X control closes the overlay. **Proves:** The panel header and close control live outside the region the new component replaced, and were neither duplicated nor displaced by it. This is the neighbour check for the overlay's own chrome.
- [ ] **Action:** Close the overlay, run `UPDATE callisto.contacts SET warning = 'CHANGED VALUE' WHERE id = <seeded-contact-id>;` then reopen the Access Manager for the same contact **without reloading the page**. **Expected:** Contact warnings reads "CHANGED VALUE". **Proves:** The overlay unmounts on close and refetches on open, so the panel can never serve a value cached from a previous session. This is the freshness requirement, and it establishes that the lifecycle satisfies it without relying on cache settings.
- [ ] **Action:** Restore the seeded contact warning, then open the Access Manager for a different contact that has no warning, watching the panel as it appears. **Expected:** No section shows the previous contact's text at any point, including briefly while loading. **Proves:** No previous contact's warning is retained between opens, including in the moment before the new fetch resolves. A warning attributed to the wrong contact is the most damaging failure this feature can produce, and it would appear only as a brief flash.

### D3: Empty Sections State Absence Explicitly

Files: [Warnings panel](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/components/RbWarningsPanel.vue), [Locale strings](../../../../../Users/dustin.thomason/atlas-front-end/src/i18n/en-US/common.json)

#### Problem

- **Current Behavior(s):** No empty state exists, because no section exists.
- **Expected Behavior(s):** An unpopulated warning reads "None"; unpopulated case remarks read "No remarks info". Every section stays labelled even with nothing to report.

#### Requirement(s)

- A user must never read blank space as "no warning recorded"; absence has to be stated.
- Warnings and remarks use different wording, because users refer to them differently.

#### Solution(s)

- Warnings use "None", taken from Figma. Remarks use "No remarks info", specified by Shaye Lankford in the ticket.
- Empty styling uses the overlay's existing de-emphasis token rather than the specification's "50% grey", which matches no token in the codebase.

#### Validation Details

Validation setup: Run the shared seed statement first, so a deliberately emptied section is distinguishable from an unseeded one.

- [ ] **Action:** Run `UPDATE callisto.contacts SET warning = '' WHERE id = <seeded-contact-id>;` and open the Access Manager for that contact. **Expected:** The "Contact warnings" heading is still present and its body reads "None" in italic, de-emphasized text — not blank space. **Proves:** An absent warning produces an explicit statement of absence rather than empty space, so the user can tell "RB holds nothing" apart from "this did not load". A blank section is indistinguishable from a broken one.
- [ ] **Action:** Run `UPDATE callisto.cases SET remarks_html = NULL WHERE id = 1001;` and reopen. **Expected:** The "Case remarks" body reads "No remarks info", which is different text from "None". **Proves:** Remarks carry their own empty wording instead of sharing the warnings' "None", which the ticket calls an intentional distinction. Identical wording would collapse two different kinds of absence into one message.
- [ ] **Action:** Run `UPDATE callisto.contacts SET warning='' WHERE id=<seeded-contact-id>; UPDATE callisto.firms SET warning='' WHERE id=9001; UPDATE callisto.cases SET warning=NULL, remarks_html=NULL WHERE id=1001;` and reopen. **Expected:** All four headings are visible; the three warning sections read "None"; Case remarks reads "No remarks info". **Proves:** Every section handles absence independently, and the panel does not collapse, hide itself, or fall through to the failure message when nothing at all is available. All-empty is the most likely real state until replication ships.
- [ ] **Action:** Re-run the shared seed statement. **Expected:** All four sections show their values again. **Proves:** The empty state is driven by the data rather than by a stuck render, and the environment is restored for the objectives that follow.

### D4: Failed Fetch Never Reads Empty

Files: [Warnings panel](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/components/RbWarningsPanel.vue), [Warnings composable](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/composables/useAccessManagerWarnings.ts)

#### Problem

- **Current Behavior(s):** No fetch exists, so no failure state exists.
- **Expected Behavior(s):** When the request fails, the panel shows "Warnings/remarks failed to load" in place of all four sections, and the user can still complete the access work.

#### Requirement(s)

- A failure must never be indistinguishable from an empty record; that confusion is the defect this objective exists to prevent.
- The failure message replaces the sections rather than sitting beside empty ones.
- A slow or failed warnings request must not block the rest of the Access Manager.

#### Solution(s)

- The panel branches on error before loading and before the sections, so no empty state can render during a failure.
- The warnings query is deliberately kept out of the overlay's loading state, which is fed only by the tracks query.
- Failure wording specified by Shaye Lankford in the ticket.

#### Validation Details

Validation setup: Run the shared seed statement and confirm D2's first check passes, so a working panel is distinguishable from a failing one. Then stop the Callisto process listening on port 3004.

- [ ] **Action:** With Callisto stopped, open the Access Manager for the seeded contact. **Expected:** The panel shows "Warnings/remarks failed to load" and **none** of the four section headings appear. **Proves:** A fetch failure is reported as a failure rather than absorbed into the empty state. This is the check that separates "unavailable" from "nothing recorded" - a warning that failed to load must never look like a warning that does not exist.
- [ ] **Action:** With that failure on screen, read the whole panel. **Expected:** Neither "None" nor "No remarks info" appears anywhere. **Proves:** The failure branch and the empty branch are mutually exclusive in the template, so the two cannot render together and produce a self-contradicting panel.
- [ ] **Action:** With Callisto still stopped, use the overlay's left column to expand a track and toggle a deliverable type. **Expected:** The left column still renders and responds; the warnings failure has not blocked the access work or prevented the overlay from opening. **Proves:** The warnings query is not folded into the overlay's blocking loading state, so a warnings outage cannot prevent the access work the overlay exists to do. This is the non-blocking requirement, and the left column is the neighbour most at risk from getting it wrong.
- [ ] **Action:** Restart Callisto on port 3004, close the overlay, and reopen it. **Expected:** The four sections return with their seeded values and the failure message is gone. **Proves:** The failure state is transient and clears on the next open with no page reload, so a temporary outage does not leave the panel permanently broken for the session.

### D5: Case Remarks Render Sanitized And Contained

Files: [Warnings panel](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/components/RbWarningsPanel.vue), [Panel styles](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/components/RbWarningsPanel.module.scss)

#### Problem

- **Current Behavior(s):** No remarks are rendered. Nothing else in the codebase renders RB-authored HTML except one notification component.
- **Expected Behavior(s):** Remarks display with their emphasis intact while anything that would act rather than be read is removed, and the markup cannot affect anything outside the panel.

#### Requirement(s)

- Raw RB HTML must never reach the page; it is always routed through a sanitizer.
- The emphasis an author applied survives, because that emphasis carries meaning.
- Remarks markup changes only the remarks.

#### Solution(s)

- Sanitized with DOMPurify called bare, following the specification and the repository's only other HTML-rendering site. The allowlist in the ClickUp ticket was not applied: the bare call already removes everything the criteria forbid, and the allowlist would silently drop formatting nobody agreed to drop.
- Rendered inside a contained wrapper so width and overflow cannot escape the panel.

#### Validation Details

Validation setup: Run the shared seed statement, then open devtools on the Atlas tab. **Every check here must be done in the browser.** DOMPurify does not sanitize correctly under the project's test environment — probed directly on 2026-08-20, `<p>Safe</p><script>x=1</script>` returned `Safe<script>x=1</script>`, removing the safe tag and keeping the script. The component specs therefore prove only that raw HTML is always routed through the sanitizer, never that anything is stripped.

- [ ] **Action:** Run `UPDATE callisto.cases SET remarks_html = '<p>Safe text</p><script>window.__pwned=1</script>' WHERE id = 1001;` open the Access Manager, then type `window.__pwned` in the devtools console. **Expected:** The panel shows "Safe text"; the console returns `undefined`; and the Elements panel shows no `<script>` inside the Case remarks section. **Proves:** The sanitizer strips executable markup before `v-html` inserts it, so RB-authored HTML cannot execute inside Atlas. This has to be checked in a browser: the sanitizer does not behave correctly under the project's test environment, so no automated spec establishes it.
- [ ] **Action:** Run `UPDATE callisto.cases SET remarks_html = '<p onclick="window.__clicked=1">Click me</p>' WHERE id = 1001;` reopen, click the text, then check `window.__clicked`. **Expected:** The text displays; the console returns `undefined`; the rendered element carries no `onclick` attribute. **Proves:** Event-handler attributes are stripped, not only element tags. A configuration that removes `<script>` but permits `onclick` passes the previous check and fails here.
- [ ] **Action:** Run `UPDATE callisto.cases SET remarks_html = '<p>Note</p><iframe src="https://example.com"></iframe>' WHERE id = 1001;` and reopen. **Expected:** "Note" displays and no `<iframe>` exists in the Case remarks section. **Proves:** Embedded external content is removed, so a remark cannot pull a third-party frame into the panel.
- [ ] **Action:** Run `UPDATE callisto.cases SET remarks_html = '<p style="color:#b00;font-size:18px"><strong>Rush</strong> delivery</p>' WHERE id = 1001;` and reopen. **Expected:** "Rush" is bold, the text is red, and the font is visibly larger than the warning sections above it. **Proves:** Sanitization removes what is dangerous without stripping the formatting the feature exists to show. A sanitizer configured too tightly passes every hostile check above and still makes this feature useless.
- [ ] **Action:** Run `UPDATE callisto.cases SET remarks_html = repeat('ABCDEFGHIJ', 40) WHERE id = 1001;` and reopen. **Expected:** The unbroken string wraps inside the panel; the overlay does not widen and the page does not scroll sideways. **Proves:** The panel constrains content it did not author, so one long unbroken token cannot widen the overlay or push the page sideways. Remarks text comes from RB and has no length or content guarantee.
- [ ] **Action:** Re-run the shared seed's case statement. **Expected:** The formatted remark renders as in D2. **Proves:** The hostile-markup edits are fully reverted and the normal render is intact, so no later objective inherits a mangled remarks value.

### D6: Long Content Scrolls Inside Panel

Files: [Panel styles](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/components/RbWarningsPanel.module.scss), [Overlay styles](../../../../../Users/dustin.thomason/atlas-front-end/src/callisto/pages/JobProceedingPages/ProceedingDetailPage/components/AccessManagerOverlay/AccessManagerOverlay.module.scss)

#### Problem

- **Current Behavior(s):** The panel's parent column is `overflow: hidden`, so content taller than the column is clipped with no scrollbar and no indication anything is missing.
- **Expected Behavior(s):** Content taller than the panel scrolls inside it, and the Save and Cancel controls stay reachable.

#### Requirement(s)

- A warning or remark longer than the available space can be read in full.
- Reading it does not displace the access work.

#### Solution(s)
