### Seed statement — run once before any browser objective

```sql
-- 1. A firm with a warning.
INSERT INTO callisto.firms (id, name, address, city, state, zip, country, directions,
       main_phone, alt_phone, toll_free_phone, fax, firm_type_id, warning, is_active,
       created_at, updated_at)
VALUES (9001, 'Tool Time LLP', '123 Binford Ave', 'Detroit', 'MI', '48201', 'US', '',
        '', '', '', '', 1, 'Firm is on credit hold - confirm before releasing', true,
        now(), now())
ON CONFLICT (id) DO UPDATE SET warning = EXCLUDED.warning;

-- 2. Give the named contact a warning and attach it to that firm.
--    The id is explicit on purpose: an earlier version selected whichever active
--    contact sorted lowest, so the script could not tell you which row it hit.
UPDATE callisto.contacts
SET warning = 'Do not release deliverables before payment clears',
    account_id = 9001
WHERE id = 800001;

-- 3. Give the case a warning and remarks.
UPDATE callisto.cases
SET warning = 'Protective order in place - do not release to opposing counsel',
    remarks_html = '<p style="color:#b00"><strong>Rush</strong> delivery agreed with counsel.</p>'
WHERE id = 1001;

-- 4. Confirm the seed actually reached the database.
--    This raises instead of returning a row. The previous version used CROSS JOIN,
--    so it produced a reassuring result even when nothing had been seeded; and it
--    bypassed the proceeding -> job -> case path the endpoint actually walks.
DO $$
DECLARE cw text; fw text; caw text; crh text;
BEGIN
  SELECT ct.warning, fm.warning, cs.warning, cs.remarks_html
    INTO cw, fw, caw, crh
  FROM callisto.proceedings p
  JOIN      callisto.jobs     j  ON j.id  = p.job_id
  LEFT JOIN callisto.cases    cs ON cs.id = j.case_id
  LEFT JOIN callisto.contacts ct ON ct.id = 800001
  LEFT JOIN callisto.firms    fm ON fm.id = ct.account_id
  WHERE p.id = 3001;

  IF coalesce(cw, '')  = '' THEN RAISE EXCEPTION 'Contact warning empty - statement 2 did not take.'; END IF;
  IF coalesce(fw, '')  = '' THEN RAISE EXCEPTION 'Firm warning empty - statement 1 did not take, or contact 800001 account_id does not point at firm 9001.'; END IF;
  IF coalesce(caw, '') = '' THEN RAISE EXCEPTION 'Case warning empty - statement 3 did not take, or proceeding 3001 does not reach case 1001.'; END IF;
  IF coalesce(crh, '') = '' THEN RAISE EXCEPTION 'Case remarks empty - statement 3 did not take.'; END IF;

  RAISE NOTICE 'Seed verified: all four values present along the paths the endpoint queries.';
END $$;
```

**Which values are per-contact and which are per-case.** The endpoint answers with two queries against different keys. `findContactAndFirmWarnings(contactId)` gives Contact warnings and Firm warnings, so those change as you move between contacts. `findCaseWarnings(proceedingId)` walks proceeding to job to case, so Case warnings and Case remarks are a property of the **proceeding** and are identical for every contact on it. Seeing the same case warning on two different contacts is correct. Seeing the same contact or firm warning on two different contacts is not.

**Re-run the seed after every database rebuild.** A rebuild restores fixture-only state - 21 contacts, 4 cases, 0 firms - and removes everything the seed wrote. This is the single most likely reason the panel reads empty when the seed appeared to work earlier in a session: the seed was correct and committed, and a later rebuild erased it. Verified 2026-08-24: this database was rebuilt at 13:52:30 UTC, and from that moment no write reached `contacts`, `firms` or `cases` until the seed was re-run.

**Fixture baseline.** A freshly rebuilt database holds 21 contacts, 4 cases, 4 jobs, 5 proceedings, **0 firms and 0 grants**. Firms and grants being empty is the shipped state, not leftover damage — which is why the seed creates a firm, and why the Client Access list is empty in every fresh session.

**How to open the Access Manager.** Two entry points exist and only one works today.

- **Entry point 1 — contact search.** Open the Access Manager URL, open the contact management panel, search for the contact you seeded, and select it. This works now and every objective below uses it unless stated otherwise.
- **Entry point 2 — Client Access list row.** Requires an existing access grant. The database has **0 grants**, so the list is empty and this path is unreachable. Covered by D10, which is `Blocked`.

### D1: Endpoint Returns Four Warning Values

Files: [Warnings repository](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/infrastructure/repositories/access-manager-warnings.repository.ts), [Transaction script](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/domain/transaction-scripts/fetch-access-manager-warnings-ts/fetch-access-manager-warnings.transaction.script.ts), [Response mapper](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/application/controllers/actions/access-manager-warnings-action/access-manager-warnings.mapper.ts), [Action](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/application/controllers/actions/access-manager-warnings-action/fetch-access-manager-warnings.action.ts)

#### Problem

- **Current Behavior(s):** No read path exists from `contacts.warning`, `firms.warning`, `cases.warning` or `cases.remarks_html` to any HTTP surface, so Atlas cannot obtain these values.
- **Expected Behavior(s):** `GET /callisto/granting-client-access/contacts/contactId/:contactId/proceedingId/:proceedingId/warnings` returns all four values in one nested response, with empty and whitespace values reported as null.

#### Requirement(s)

- One request returns all four values, so the panel has a single atomic success or failure.
- The contact and firm resolve from the contact id; the case resolves from the proceeding id through its job.
- Empty strings and nulls collapse to one representation, because the source columns disagree on nullability.

#### Solution(s)

- A repository holding both queries, called twice by one transaction script, because the architecture rules forbid one script calling another.
- An application-layer mapper performs the normalization, because repositories and services may not import mappers.
- Built on `FetchClientAccessListAction` as the template rather than the action the specification names, which has neither a mapper nor a guard.

#### Validation Details

Validation setup: Run the shared seed statement. Open the Access Manager URL with devtools open on the Network tab, filtered to `warnings`.

This objective's requirement is the API contract itself - a new endpoint and its response shape - so technical inspection is warranted here under the template's rule 4. Every other objective below is proved from the product UI. The normalization, left-join and inactive-contact behaviours that earlier revisions checked by hand are covered by [the mapper spec](../../../../../Users/dustin.thomason/callisto-back-end/src/granting-client-access/contacts/application/controllers/actions/access-manager-warnings-action/__specs__/access-manager-warnings.mapper.spec.ts) and by the integration spec recorded under D7, and are not repeated as manual steps.

#### Problem

- **Current Behavior(s):** No fetch exists, so no failure state exists.
- **Expected Behavior(s):** When the request fails, the panel shows "Warnings/remarks failed to load" in place of all four sections, and the user can still complete the access work.

#### Requirement(s)

- A failure must never be indistinguishable from an empty record; that confusion is the defect this objective exists to prevent.
- The failure message replaces the sections rather than sitting beside empty ones.
- A slow or failed warnings request must not block the rest of the Access Manager.

#### Solution(s)

### D5: Case Remarks Render Sanitized And Contained
