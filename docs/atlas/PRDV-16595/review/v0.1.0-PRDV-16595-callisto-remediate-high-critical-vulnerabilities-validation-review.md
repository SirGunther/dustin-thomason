## Review Summary

Callisto satisfies the ticket's stated acceptance criterion today, and the override block that achieves it has been fully characterised: of eight entries, three are load-bearing and five are inert and safely deletable. That is the measured half of this review.

The unmeasured half is where the actual work sits. The ticket's real ask — Larry's, from standup — is upstream: remediate `@planetdepos/pathfinder-observability-pkg` so consuming apps can stop overriding. That objective is **Blocked**, and not on effort or access: `0.2.13` is the newest published release, so no consumer can resolve the OpenTelemetry chain by bumping a dependency. A new Pathfinder release is the epic's critical path, and until it ships, overriding is the only option available to Callisto, nova-orbital, and any future consumer.

One finding arrived unlooked-for and is the most consequential item here. Removing the `tar` override exposes **one critical-severity vulnerability** via `sqlite3` → `node-gyp` → `cacache`/`make-fetch-happen` → `tar`. It is the only critical anywhere in PRDV-16423, and Callisto's compliance with the epic's acceptance criteria currently depends on an override suppressing it. That is precisely the fragility Larry described — *"you can get away with override, but at some point we got to kind of stop, kind of nip it"* — and it warrants a decision rather than a quiet pass.

**Update, 2026-08-27 — eight of nine masked highs eliminated at source.** Pathfinder published `0.2.14`; Callisto upticked to it and to `@nestjs/swagger@11.4.7`, and **both override blocks were deleted**. The swagger override proved redundant: `11.4.7` resolves `js-yaml 5.3.0`, already outside the vulnerable `4.x` range. A clean rebuild returned audit `0`, lint `0`, and the full suite green (411 suites, 2165 tests). Callisto's `overrides` block now contains **only `tar`**, masking the one remaining critical plus four highs.

No release-level failure was established.

**Update, 2026-08-25 evening.** The upstream fix is no longer hypothetical. Pathfinder's bump is applied and verified green on `PRDV-16595-otel-bump` — audit, build, lint and tests all exit `0`, with `propagator-jaeger` at `2.10.0`. D4's blocker has therefore narrowed from *"no fix exists"* to *"the fix is not published yet"*, which is a materially different position. D3 sits on branch `PRDV-16595` at `7d9a6926`; PR #432 was closed deliberately rather than merged. D5 remains the one item awaiting a decision this review cannot make.

#### The decision, separated into its two independent questions

These were previously described together, which made them impossible to weigh. They are different questions, they have different answers, and they have different remedies.

##### Question 1 — Is this a live production security exposure?

**Almost certainly not.** The chain is:

```
sqlite3 5.1.7            (declared in "dependencies")
  └── node-gyp 8.x       native-module build tool
        └── make-fetch-happen 8-9
              └── http-proxy-agent 4.0.1
                    └── @tootallnate/once <2.0.1   <-- the advisory
                          GHSA-vpq2-c234-7xj6, Incorrect Control Flow Scoping
```

`node-gyp` compiles native bindings at **install time**. `make-fetch-happen` is how it fetches prebuilt binaries. None of that code path executes while the Callisto service is running, so there is no request an attacker can send that reaches it.

**But it is still present in the production image**, because `sqlite3` sits in `dependencies` rather than `devDependencies`. So it is image surface area and it will show up in any image scan — which is exactly what Karl Amber's Trivy work surfaces.

##### Question 2 — Does it block the CI audit gate?

**Yes, and only one thing changes that.** The gate is `npm audit --audit-level=high` run on the **full tree, dev dependencies included** (`node-service-ci.yml`). Two consequences that are easy to get backwards:

- Moving `sqlite3` to `devDependencies` does **not** help the gate. The gate still sees it.
- The gate passes today **only** because the `tar` override forces a patched `tar`, which breaks the chain above it.

##### The underlying oddity worth naming

`sqlite3` is declared as a production dependency, but its **only** consumer anywhere in the codebase is `src/test-utils/test-database.module.ts` — an in-memory test database helper. On the evidence it is a **misclassified dependency**, not a production one.

##### Options, scored against both questions

| Option | Q1: removes prod exposure? | Q2: keeps the gate green? | Cost / risk |
| --- | --- | --- | --- |
| **A.** Keep the `tar` override, change nothing | No — still in the image | Yes | Zero effort. A critical stays masked indefinitely, invisible to the gate |
| **B.** Move `sqlite3` to `devDependencies` | **Yes** — leaves the prod image entirely | Yes, *because the `tar` override stays* | Low. One check needed: confirm `test-utils` is excluded from the production build so nothing at runtime imports it |
| **C.** Upgrade to `sqlite3@6.x` | No — still in the image | Yes, and without needing the override | Breaking major. `npm audit fix --force` proposes `sqlite3@6.0.1`; native-binding behaviour would need retesting |
| **B + C.** Move it *and* upgrade | Yes | Yes, override could then be dropped | Highest effort; the only option that ends with no override and no masked critical |

##### Recommendation

**Option B.** It is the only low-risk change that addresses Question 1, and Question 1 is the one that carries real-world consequence. It also corrects a genuine misclassification rather than working around it. It does **not** let the `tar` override be removed — that needs C — but nothing today requires removing it.

What B does **not** do is make the masked critical go away. It relocates it out of production and leaves the gate relying on the override, which should be recorded as an accepted risk with an owner rather than silently kept.

**This recommendation is not a decision.** Whether a masked critical is tolerable, and whether a breaking `sqlite3` major is worth scheduling, is Larry and Derrick's call.
