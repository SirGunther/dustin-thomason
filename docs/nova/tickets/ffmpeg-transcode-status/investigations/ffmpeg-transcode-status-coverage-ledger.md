## Evidence snapshots

### Nova

- Baseline: `nova-back-end@58a6182` (`PRDV-16398`).
- `FfmpegAdapter.transcode()` spawns `/usr/local/bin/ffmpeg` with piped stdout/stderr but does not parse progress.
- `TranscoderPort.transcode()` returns `Promise<void>`.
- `ProbeDurationStep` obtains total seconds before `TranscodeStep`.
- Terminal outbox events are coupled to inbox state in transaction paths.
- Nova's completed converter uses the origin request ID as event/envelope ID; failed includes `originEventId`.

### Messaging

- Baseline: `nova-orbital-back-end@bfd5094`.
- Nova outbox default poll interval is 5,000 ms and batch size is 20.
- Installed relay code publishes using the event's `eventType` as routing key.
- Production task concurrency, deployed overrides, queue depth, and retention were not present in the inspected local code.

### Callisto

- Baseline: `callisto-back-end@3ecab1b8` (`PRDV-16402-reland`).
- Both form submission and post-submission upload can create a transcode request.
- Proceeding inbox registration contains completed only, not failed or progressed.
- ~~Completed listener binds `callisto.proceeding.file.video-transcode-completed.v1`; Nova publishes `nova.proceeding.file.video-transcode-completed.v1`.~~ **Corrected 2026-08-03:** the listener _consumes from a queue named_ `callisto.proceeding.file.video-transcode-completed.v1` (constant: `CALLISTO_..._INBOX_QUEUE`). It binds nothing — `buildRabbitSubscribeOptions` forwards only `queue`/`connection`/`createQueueIfNotExists: false`, and `routingKey` is never read at runtime. Dispatch matches the envelope's event type, which is Nova's. Consumer-namespaced queue fed by a producer-namespaced routing key is the intended design.
- `file_derivations` is created after success and requires a derived file; it is not an active-run store.
- Completion includes an external copy followed by derivative persistence, so Nova completion is only the beginning of Callisto `finalizing`.
- Global auth middleware authenticates the AJSF file GET, but that endpoint intentionally applies no proceeding restriction or job-task ownership guard. The AJSF form-load endpoint does verify job-task ownership. The guarded proceeding-detail file GET is a distinct authorization surface.
- `IS_VIDEO_TRANSCODE_ENABLED` is evaluated from the initiating user's Cognito feature-flag claim on both submit and completed AJSF upload.

### Atlas

- Baseline: `atlas-front-end@102e034d`.
- Proceeding-file queries use a two-minute stale time and have no periodic refetch.
- No EventSource/WebSocket mechanism was found.
- Relevant reusable rows are the AJSF/read-only `FileListItem` and proceeding-detail `ProceedingFileTableDataRow`.
- Submit-time navigation to My Jobs makes global placement an unresolved product choice.
- The concrete LTR path is `/callisto-stuff/my-jobs?tab=submitted` → `/callisto-stuff/submitted-job-submission-form/:jobTaskId`; internal proceeding detail is `/callisto-stuff/job/:id/proceeding/:proceedingId`.
- Atlas' generic feature-flag query is cached for five minutes and has no transcode-status constant today.

## Assumptions challenged during investigation

| Initial premise                                                            | Evidence-based correction                                                                                                                                                                                                                                                                                                                                                 |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FFmpeg has a conversion indicator that can simply be returned to Callisto. | FFmpeg has structured process output, but Nova currently discards it and Callisto has no lifecycle store or progress contract.                                                                                                                                                                                                                                            |
| Percent complete represents the whole operation.                           | It represents only FFmpeg processing. Input preparation and two output-persistence phases require indeterminate stages; 100% belongs to end-to-end Callisto completion.                                                                                                                                                                                                   |
| Existing terminal messaging can be extended without preconditions.         | ~~The locally inspected completed listener routing key differs from the event type Nova publishes and must be proved or corrected.~~ **Reverted 2026-08-03 — the original premise was closer to right.** The completion route is consistent in code; extending it needs infra bindings for the new event type, which is ordinary release work rather than a precondition. |
| A config field named `routingKey` describes how the listener is bound.     | It is never read at runtime. Confirming that a load-bearing config value is actually _consumed_, not merely declared, is now part of this method.                                                                                                                                                                                                                         |
| “Live” implies a particular technology.                                    | Existing durable polling can likely produce multi-second updates; the actual latency SLO must be agreed and measured before choosing push infrastructure.                                                                                                                                                                                                                 |
| A derivative record can store progress.                                    | It cannot exist before a non-null derived file exists and is currently written only after success; a separate run model is required.                                                                                                                                                                                                                                      |

## Remaining frontier

These are intentional investigation boundaries or evidence gaps, not silently completed work:

1. Execute `/usr/local/bin/ffmpeg -version` and a structured-progress fixture inside the actual Nova container/CI image. **Downgraded 2026-08-03 to confirmatory** — the shipped binary's option strings have been inspected; only the version string and live behavior remain unread.
2. Inspect the source repository and release pipeline for `@planetdepos/orbital-docking-protocol`.
3. Document the deployed RabbitMQ exchanges/queues/bindings, including retry and DLQ, and add the progressed event's binding. **Rescoped 2026-08-03** — the original wording ("whether any external routing-key rewrite exists") presumed a mismatch that does not exist. No rewrite is needed; the topology simply lives outside these repositories.
4. Collect production/sandbox concurrency, duration, outbox/inbox lag, queue depth, and shared-event volume.
5. Locate or define deployed outbox/inbox retention and lifecycle-row cleanup policy in infrastructure repositories.
6. Obtain one named affected user/job and a dated product urgency/release trigger.
7. Rebase/reinspect target branches before specification: local Nova Orbital was behind by two commits and Atlas by six.
8. Decide whether My Jobs, proceeding details, AJSF upload, or all three are required presentation surfaces.
9. Define product-approved freshness, stale-run thresholds, failure copy, completed-state persistence, and active-file deletion policy.
10. Test Callisto's permanent inbox-failure/reconciliation behavior under an output-copy or terminal DB failure.
11. Collect actual Cognito assignment/cohort data for `IS_VIDEO_TRANSCODE_ENABLED`; repository code establishes semantics but not which LTRs or environments currently receive it.
12. Approve the actor/route authorization matrix and decide whether a separate UI rollout flag is required.

## Confidence statement

Confidence is **high** that structured FFmpeg progress can be observed and that the implementation spans protocol, Nova, Callisto persistence/API, and Atlas. Confidence is **medium** on the proposed polling cadence and event bounds because production load and deployed topology were not available.

**Revised 2026-08-03 after the validation pass.** Confidence on FFmpeg support rises from medium to **high** — the option strings were read out of the binary the Dockerfile ships. Confidence in the recommended architecture is **unchanged and high**; it survived re-verification of every load-bearing claim. One claim did not: the reported completed-route routing-key mismatch was **withdrawn**, having read a queue name as a binding without checking whether the config field is consumed at runtime. That correction removed a blocking gate rather than adding one. Deployed load and messaging topology remain the two genuinely unread areas. No implementation authorization should be inferred from this ledger.
