# FFmpeg Transcode Status — Design Decisions and Implementation Considerations

**Status:** Open decision register; no implementation authorized  
**Created:** 2026-08-03  
**Purpose:** Isolate the behavioral, product, security, rollout, and operational decisions that must be settled before the FFmpeg transcode-status investigation can become an implementation specification.  
**Canonical investigation:** `investigations/ffmpeg-transcode-status-investigation.md`  
**Coverage record:** `investigations/ffmpeg-transcode-status-coverage-ledger.md`

## Bottom line

The original investigation established that progress is technically viable. This register identifies the choices that code cannot make for the team.

The recommended experience, pending owner approval, is:

1. **LTR entry surface:** show an active-conversion summary on `/callisto-stuff/my-jobs?tab=submitted`, because form submission currently sends the LTR there.
2. **LTR detail surface:** show per-file stage and percentage on `/callisto-stuff/submitted-job-submission-form/:jobTaskId`, which is already reached from the Submitted Jobs tab and is ownership-checked when the form loads.
3. **Internal operations surface:** show the same per-file status on `/callisto-stuff/job/:id/proceeding/:proceedingId`, subject to its existing restriction-level authorization.
4. **Authorization:** do not expose transcode state by merely widening the current AJSF file-list GET. That endpoint is authenticated but intentionally lacks proceeding-restriction and job-task-ownership guards. Add an owner-scoped status read or add equivalent authorization.
5. **Feature flags:** keep `IS_VIDEO_TRANSCODE_ENABLED` as the gate for creating **new** requests. If UI rollout needs a separate gate, use a new display flag; never turn off backend consumption or hide an already-active run because the initiation flag changed.
6. **Lifecycle:** retain `queued → preparing → transcoding (0–99%) → finalizing → completed (100%)`, with `failed` terminal from any active stage.

These are recommended defaults, not locked decisions. The first specification pass should resolve the “Before spec” rows below before choosing files or estimates.

## Recommended 30-second experience

An assigned LTR submits a job containing two eligible videos. Atlas takes them to Submitted Jobs, where the job row says “Converting 2 videos.” Opening the row returns to the submitted job form. Each original file remains visible with its own status: queued, preparing, a monotonic conversion percentage, then finalizing. A page refresh reconstructs the same state. The first completed derivative appears beside its source while the second continues independently. If the second fails, its row says that conversion failed and the original is still available; the existing failure email directs the LTR to the same Submitted Jobs location. Internal staff with appropriate proceeding restriction access see the same lifecycle on proceeding detail. No browser needs to remain open for correctness.

## Decision order

Resolve decisions in this order because later choices depend on earlier ones:

1. **Audience and URLs:** who must see status, on which routes, under what authorization.
2. **Behavioral contract:** stages, percentage semantics, terminal/stale behavior, and user actions.
3. **Flag and rollout contract:** what gates new work, what gates display, and what remains always on.
4. **Data/API contract:** run identity, history, secure projections, correlation, retention, and backfill.
5. **Freshness and capacity:** cadence, polling, supported concurrency, storage, and SLO.
6. **Validation and rollout:** actor matrix, failure injection, feature-flag cohort, monitoring, rollback, and runbook.
