## Open items

### UX-001 — Red "unavailable" styling is overused for expected, non-blocking states (verified live)

- **Where observed:** the live Logged Items pane — 6 of 7 rows carry a red `Optional classification unavailable · editing unaffected` badge (`styles.css:308` `.classification-suggestion.unavailable`); the footer System Status panel shows `storage-session: unavailable`, `classification: unavailable`, `folder-opening: unavailable` in the same red (`styles.css:450` `.service-chip.unavailable`), rolled up into a red "3 service issues" summary.
- **Problem:** in the browser-bridge POC host, classification/storage-session/folder-opening are *expected* to be unavailable by design (`product-and-layout-decisions.md` AD-018/AD-024 — these are desktop-only capabilities). But the UI renders that expected, harmless state in the same alarm-red used for real failures, on nearly every row and in the footer summary. The badge's own text says "editing unaffected," yet the color says "something is wrong" — the two signals contradict each other, and with 6/7 rows red the color stops meaning anything.
- **Requirement:** color must track actual severity — an expected, host-scoped capability gap should not use the same visual language as a real failure.
- **Candidate solution:** give "capability not available on this host" its own neutral/muted treatment (e.g., reuse `--text-muted` instead of `--red`), and reserve red for states that are actually unexpected/actionable (e.g., `classification.failed`, which already has separate CSS at `styles.css:308` but currently looks identical to `.unavailable`).
- **Resolved:** recolored `.classification-suggestion.degraded`/`.unavailable` to `var(--text-muted)`/`var(--line)`, since both states' own text unconditionally says "editing unaffected" (`describeClassification`, `ui/ui-state.mjs:56-73`). Scoped narrowly — the `service-chip.unavailable` footer chips were left red, since a real service being down is a legitimate signal there, not a labeled non-issue like the classification badge.

### UX-002 — Service-status chip text truncates mid-word with no way to read the full value (verified live)

- **Where observed:** the System Status panel chip for the logged-item pipeline renders as `logged-item-pipeline: avai…` — `styles.css:447` caps `.service-chip` at `max-width: 145px` with `text-overflow: ellipsis`, which lands mid-word on this particular label.
- **Problem:** there is no `title` attribute or other way to read the full chip text, so a user sees a clipped, slightly odd-looking word fragment with no way to confirm what it actually says.
- **Requirement:** truncated status text must remain fully readable on demand.
- **Candidate solution:** set `title` to the untruncated `"<service>: <status>"` string wherever these chips are rendered (`ui-state.mjs`, not modified here), and/or widen the chip's max-width slightly since 145px is tight for labels like `logged-item-pipeline`.
- **Resolved:** `renderServices()` (`app.js:617-627`) now sets `chip.title` to the full `"<capability>: <status>"` label plus the service message when one exists; `.service-chip` max-width widened from 145px to 190px (`styles.css`).

### UX-003 — Hover colors on primary buttons bypass the design tokens with hardcoded hex + `!important` (static review)

- **Where:** `styles.css:544` (`.drawer-folder-button:hover`), `:570` (`.settings-footer .button:hover`), `:587` (`.button-danger:hover`) — all three hardcode a literal hex hover color with `!important` instead of deriving from `--accent`/`--red`.
- **Problem:** three separate buttons each hand-picked a slightly-brightened hex value instead of one shared "brightened accent" token, and used `!important` to win instead of fixing specificity. If `--accent` or `--red` ever changes, these three hovers silently drift out of sync with the rest of the palette.
- **Requirement:** hover states must derive from the same tokens as the resting state, with no `!important` needed.
- **Candidate solution:** add `--accent-hover` / `--red-hover` tokens beside the existing `--accent`/`--red` in `:root` (styles.css:13-20) and reference them from all three rules; drop the `!important`s once the specificity conflict causing them is identified and fixed at the source (per the "fix the rule, not the symptom" guardrail).
- **Resolved:** added `--accent-hover`/`--red-hover`/`--red-hover-border` tokens. The actual specificity conflict was `.button:hover:not(:disabled)` (3 class-level selectors) outranking the two-class `.drawer-folder-button:hover`/`.button-danger:hover` — fixed by qualifying both with `.button` (`.button.drawer-folder-button:hover`, `.button.button-danger:hover`), which ties specificity and wins on source order like `.settings-footer .button:hover` already did. No `!important` remains on any of the three.

### UX-004 — Icon-only destructive/adjacent controls have no visual weight difference (static review)

- **Where:** `index.html:43-48` — `closeSessionButton` (destructive, permanent per PD-008 in `product-and-layout-decisions.md`) and `aiProviderButton` (benign settings) both use the identical `.icon-button` style (`styles.css:150-163`), same size, same muted color, sitting side by side.
- **Problem:** the only thing stopping an accidental "Close session" click is the confirmation modal — the button itself gives no visual hint it's more consequential than the settings gear next to it. That's a real risk for a PD-008 "irreversible finalization boundary" action.
- **Requirement:** a destructive action adjacent to a benign one should be visually distinguishable before the confirmation step, not only after.
- **Candidate solution:** give `.close-session-button` a subtle resting-state tint (e.g., faint red border/icon color, similar to how `.button-record` already uses `--red-soft`) so it reads as "different" at a glance.
- **Resolved:** `.close-session-button` now rests at a muted red icon color (`#d99a96`) and brightens to `--red-soft`/`#ffb5af` on hover, distinguishing it from `.ai-provider-button` at rest, not only after the confirmation modal opens.

### UX-005 — Row copy action is invisible without hover, with no touch/keyboard-discoverable fallback (static review)

- **Where:** `styles.css:349-353` — `.row-copy { opacity: 0; }`, revealed only via `:hover` or `:focus-visible` on the row.
- **Problem:** the responsive breakpoints at `840px` and `480px` (styles.css:610-629) indicate narrower/touch-capable layouts are a deliberate target, but a hover-only affordance has no discovery path on a touch device — there's no `:active`/tap equivalent, and keyboard users only find it once they've already tabbed into that specific row.
- **Requirement:** every row-level action available on desktop should have a non-hover discovery path on touch/narrow layouts.
- **Candidate solution:** at the `840px` breakpoint, drop `opacity: 0` on `.row-copy` so it's always visible (matches the general pattern of narrow layouts trading density for discoverability, already used elsewhere in that media query).
- **Resolved — with a correction:** used `@media (hover: none)` instead of the `840px` width breakpoint, since hover capability (not viewport width) is the actual thing being tested — a wide touch device would still need this and a narrow mouse-driven window wouldn't. Applied to both `.row-copy` and the new compact `.source-range` icon from UX-008.

### UX-006 — Pane title and status badge compete for the same shrinking row (static review)

- **Where:** `styles.css:196-207` — `.pane-title-line` holds `h2` (ellipsis-truncating), `.count-badge`, and `.scribe-status` (also ellipsis-truncating) all in one flex row with no explicit priority order.
- **Problem:** `h2` and `.scribe-status`'s inner text both fight for space via `flex` defaults with no `flex-shrink`/`min-width` ordering — under a longer scribe status string (e.g., "Delayed - retrying" vs. the demo's "Caught up") plus the fixed-width count badge, the title is what silently loses space first, which is backwards: the pane title ("Logged Items") is more important than a transient status string.
- **Requirement:** when space is tight, less-important transient status text should truncate before the pane's own title does.
- **Candidate solution:** give `h2` a higher shrink priority than `.scribe-status` (e.g., `.scribe-status { flex-shrink: 3; }` vs. keeping `h2` closer to its natural width), verified visually once Playwright can drive a long guidance string through the demo.
- **Resolved:** `.pane-title-line h2` now uses `flex: 1 1 auto` (claims available space first) and `.scribe-status` uses `flex: 0 3 auto` (shrinks 3x faster). Not re-verified against a long guidance string live — the demo's "Scribe caught up" status is short — worth a follow-up check once a long status string is actually observable.

### UX-007 — Column headers don't align with their own row data, because header and row resolve the same `ch`-based grid track to different pixel widths (verified live)

- **Where:** `styles.css:224-231` — `.column-labels, .data-row { grid-template-columns: 20px minmax(5ch, 7ch) minmax(0, 1fr) 28px; }` (transcript) and `.derived-labels, #derivedList .data-row { grid-template-columns: 20px minmax(5ch, 7ch) minmax(9ch, 13ch) minmax(0, 1fr) 28px; }` (derived) — the **same** `grid-template-columns` string is shared between the header (`.column-labels`) and the body rows (`.data-row`) via one selector.
- **Confirmed by measurement** (via CDP `getBoundingClientRect`, live Logged Items pane): the "Logged" time column renders **32.8px** wide in the header but **60.4px** wide in the actual row — same declared `minmax(5ch, 7ch)` track, two different rendered widths. That's because `ch` is resolved against *each grid container's own font*, and `.column-labels` explicitly sets an 8px mono font (`styles.css:237`) while `.data-row` sets no font-size of its own (only its `time`/`.editable-text` children set fonts), so its `ch` resolves against whatever font size it inherits — a different basis than the header's. The mismatch compounds rightward: in the Logged Items pane, the header's "Logged item" column starts at `x=157.75px`, but the actual logged-item text starts at `x=236.5px` — a **~79px** rightward drift, which is exactly the "timestamps pushing all the text to the far right" you're seeing.
- **Problem:** because header and row tracks aren't actually the same width despite the shared declaration, every column after the first drifts out of alignment with its own header — worst in the Logged Items pane where it visibly shoves the "Logged item" text far right of where "Logged item" the header sits.
- **Requirement:** a column's header and its row's data must occupy the same horizontal span, always — the shared grid-template-columns declaration must produce identical pixel tracks in both contexts.
- **Candidate solution:** give `.column-labels` and `.data-row` the same font-size (or switch these tracks to `minmax(Npx, Mpx)` instead of `ch`, which removes the font-dependence entirely) so `ch`, if kept, resolves identically in both places. Fix the rule they share, not one side's numbers.
- **Resolved — root cause was actually two-fold, not just font mismatch:** matching `.data-row`'s font to `.column-labels`' shrank the gap (60.4px → 46.9px) but didn't close it. The remainder was CSS Grid's default `min-width: auto` on grid items, which lets a cell's content (an 8-character `HH:MM:SS` timestamp) force the track wider than its declared `max` even when the header's short label doesn't hit that same floor — a "grid blowout," a different mechanism than the ch/font issue. Fixed by dropping `ch` entirely: column 2 is now a fixed `64px` (sized to fit the longest timestamp at 10px mono without clipping), with `min-width: 0` added to the new `.row-time` wrapper (see UX-008) so it can't blow out that fixed track. Re-measured live via CDP: header and row column-2 both render exactly 64px, and the "Logged item" header/text now start at the identical `x=118px` in both places.

### UX-009 — Reported: clicking a Logged Item's source-range only highlights part of its transcript span (not reproduced in the browser-bridge demo — needs confirmation on real data)

- **Your report:** clicking the source-range control for a logged item spanning 3 transcript entries only highlights 2 of them in the transcript pane.
- **What I checked:** drove the running browser-bridge demo live via CDP, clicked the source-range on a logged item whose `source` was `segment-3 → segment-5` (a 3-row span: `16:23:58`, `16:24:16`, `16:24:33`). `resolveSourceRangeIds` (`ui/ui-state.mjs:34-45`) is inclusive on both ends (`sequence >= low && sequence <= high`) and, in this run, all 3 rows (`segment-3`, `segment-4`, `segment-5`) received the `.source-highlight` class with matching computed styles (background `rgba(255,224,128,.11)`, inset box-shadow) — I could not reproduce a 2-of-3 result with the demo's synthetic, contiguous segment data.
- **Why this doesn't clear it:** the demo's transcript segments are perfectly sequential (`segment-0` through `segment-9`, one per second-ish, no gaps). `resolveSourceRangeIds` keys off each row's numeric `sequence` field, not the segment count implied by the id range — if a real session's segments have gaps, merges, or a `source.last_segment_id` that was computed one segment short upstream (in the extraction/logging path, not in this highlighting function), the same inclusive-range code could still under- or over-highlight relative to what a user would expect from "3 items," without this function itself being wrong.
- **Requirement:** the exact transcript span a logged item cites must fully highlight, matching the count the source range implies, on real session data — not just synthetic demo data.

### UX-010 — The source-range tooltip's own wording is what made UX-009's instance look like a bug (resolved)

- **Your follow-up:** looking at the tooltip for `logged-item-ee584dedb9eb4631d5314c11` — "Show exact source range segment-144 (00:21:50.464) through segment-145 (00:22:08.128)" — you said you'd intuitively expect it to show only the range that was actually considered, not read like it extends up to a point where nothing was collected.
- **Problem:** because segments are contiguous (each starts exactly where the previous ends), a cited range's `end_time` is *always* numerically identical to the next, uncollected segment's `start_time`. The old tooltip (`app.js`, both `createRow` and `updateRow`) stated that shared boundary as a raw "through HH:MM:SS.mmm" time, which reads as an open, continuous scan window rather than a fixed, discrete set of segments — exactly the ambiguity that made the UX-009 instance above look like a bug when it wasn't.
- **Requirement:** the tooltip must communicate "these N specific segments were considered," not a time span that happens to touch unrelated adjacent content.
- **Resolved:** added `describeSourceRange()` in `app.js`, which resolves the actual segment count via the existing `resolveSourceRangeIds` and states it explicitly — e.g. `"Exact source: 2 segments considered (segment-144 → segment-145), spoken 00:21:50.464–00:22:08.128"`. Falls back to id/time-only phrasing (no fabricated count) if the cited segments aren't in the currently loaded transcript (e.g. trimmed active history). Re-verified live via CDP: a two-segment item now shows "2 segments considered," the known three-segment item shows "3 segments considered." Same fix applied to both the `title` and `aria-label`.

### UX-012 — The source icon itself was invisible at rest, not just the text line (resolved)

- **Your follow-up:** after UX-011 removed the text line, you asked whether source context had been removed altogether — you couldn't see the icon at all.
- **Root cause, confirmed live via CDP:** `.source-range` was styled `opacity: 0` at rest (`styles.css`), only reaching `opacity: 1` on row hover/focus. A screenshot taken with no hover applied showed genuinely nothing at that position — a fully-invisible-until-hover icon gives no cue that anything is there to find, which defeats the point of replacing an always-visible text line with an icon.
- **Resolved:** default opacity raised from `0` to `.55` (visible but subdued at rest), still brightening to full opacity + accent color on hover/focus. Disabled state (`.35`) and the no-hover/touch-device override (`opacity: 1`) both stay correctly ordered under the new resting value. Re-verified: a screenshot with no hover applied now shows a faint `→` under the timestamp; computed opacity at rest reads `0.55`.
